# Verification and release automation

The verification workflow builds and tests the website, control service, TypeScript/Python clients, MCP adapter, Synapse policy, and native runtime. It also runs the offline onboarding, load, installer, backup and private-stage monitoring contracts. It receives read-only repository access and no production credentials. Action dependencies are pinned to verified commit hashes; Node, pnpm, Rust, and Synapse versions are pinned.

Deployment and backup templates remain inactive in `infra/github/`. The [manual OIDC identity check passed](../releases/production-oidc-preflight-20260912.json); it did not exercise temporary SSH access, deployment or backup transfer. Do not enable the mutation templates before the selected AWS role/instance, repository environment, alerts, and required restore drill have been verified.

The separate [production OIDC preflight](../../.github/workflows/production-oidc-preflight.yml) is manual, restricted to this repository's `main` branch and the `production` environment, and capped at five minutes. It checks out no source. The [pinned AWS action](https://github.com/aws-actions/configure-aws-credentials/blob/cbe3b392738ccf3f987d68400dafcf4b0624a56c/README.md) obtains a 15-minute OIDC session whose inline policy permits only `sts:GetCallerIdentity` and `lightsail:GetInstance`. Both require `Resource: "*"`; the instance read also requires `aws:RequestedRegion=us-east-1`. [AWS does not support resource-level scoping for GetInstance](https://docs.aws.amazon.com/service-authorization/latest/reference/list_lightsail.html), so IAM permits that read within the account and region; the workflow itself requests only the protected name and requires the returned name and ARN to match exactly. The role policy must separately permit the same regional read: a session policy cannot expand the role's permissions. There is no instance-listing permission. The job also checks account, role session and running state, and emits only sanitized results or fixed failure codes that distinguish request, response and identity-check stages. It opens no SSH access, changes no firewall, performs no S3 operation and activates nothing. A pass establishes authentication and instance identity, not application health, access cleanup, backup, deployment or restore verification.

Before a reviewed dispatch, add four **metadata-only environment secrets** to `production`: `AWS_ACCOUNT_ID`, `AWS_DEPLOY_ROLE_ARN`, `LIGHTSAIL_INSTANCE`, and `LIGHTSAIL_INSTANCE_ARN`. Take them together from independently verified **active** Terraform/AWS identity evidence; a prepared standby is not the selected host. These secret values are resource identifiers, never AWS access keys. Secrets provide log masking from the start of each step; ordinary environment variables would expose identifiers before an in-step mask ran. Missing or inconsistent identifiers fail before role assumption. The inactive existing-backup check uses these same four metadata secrets and derives its fixed backup bucket from the account. The full-deployment template still uses its existing protected variables. When the selected host changes, reconcile both that template's variables and the metadata secrets consistently before rerunning. Review the environment's branch/reviewer policy separately; this workflow does not create protection rules or change IAM trust/permissions. The active website override still requires explicit reconciliation before any full deployment; this preflight does not bypass that boundary.

The deployment template accepts a pre-uploaded production bundle ID, its reviewed manifest SHA-256, and the expected current successful production manifest hash (`none` only for the first activation). It runs only by manual dispatch from this repository's `main` branch. There is no tag trigger or image/native build during deployment. The remote activation tools at `/opt/zavliq/production-tools/` must match the workflow checkout byte for byte before their activation command runs. Bundle IDs use `REVISION-public-CONFIGURATION_PREFIX`; application provenance remains the bundle's frozen revision even when later operator tooling has its own commit. See [production bundle preparation and activation](../../infra/production/README.md).

Before installing a workflow, restrict the protected `production` environment to `main` and verify the exact immutable GitHub OIDC subject in the [hosting procedure](README.md#hosting-and-credentials). The full-deployment template requires its existing protected identifier variables; the manual backup check instead requires the four metadata secrets and three additional private inputs listed in [existing-backup checks](existing-backup-check.md). Take the instance name and exact ARN from the reviewed Terraform outputs together. The AWS action is pinned to the verified v6.2.4 commit and checks the expected account. Setting up the template does not create a GitHub environment or assume an AWS role; those live checks remain required.

The access helper accepts only the original production name or an explicitly selected `zavliq-production-recovery-<suffix>` name. Before obtaining access or changing a rule, `GetInstance` must match both that name and its exact ARN in the fixed account and `us-east-1`. The v2 journal stores the validated identity. Cleanup takes only the journal directory and continues against that saved identity even if protected environment values have changed; a reused name with a different ARN is refused. V1 journals have no ARN and must be completed with their original helper or explicitly reconciled before upgrading. Never change the active-instance IAM scope while an access journal remains outstanding. See [recovery-host adoption](recovery-host.md).

Both templates share one production host-access concurrency group. `ci-host-access.py` obtains the runner's public IPv4 address over verified HTTPS and preserves existing operator firewall rules. If access is already allowed, the run borrows it and does not remove it. Otherwise it journals ownership before requesting one TCP/22 `/32` rule. Returned Lightsail operation IDs are persisted before polling, and ownership is cleared only after a successful terminal close operation and confirmation that the exact rule is absent. A known pending open must settle before cleanup can succeed. If the open response was lost before an operation ID was recorded, cleanup attempts a close but retains ownership and reports `SSH_OPEN_OUTCOME_UNKNOWN_OPERATOR_RECONCILIATION_REQUIRED`: a delayed open is still possible, so the operator must reconcile the journal with AWS operation/CloudTrail evidence. The additional `lightsail:GetOperation` read uses `Resource: "*"` with a fixed `us-east-1` condition because this action has no resource-level scope in the [AWS IAM reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_lightsail.html). AWS-supplied host keys and an ephemeral SSH certificate are used. Cleanup attempts to close only the owned rule, then removes temporary credential files even if closure fails. The inactive manual backup template now seals the exact journal after cleanup and uploads only completed ciphertext; its runner path and approved recipient have not yet been live-verified. The separate full-deployment template still has a raw-journal artifact path and remains blocked as written. That journal contains private instance, temporary runner CIDR, ownership and operation metadata even though it contains no credential files. [Repository readers can download workflow artifacts](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/download-workflow-artifacts); log masking does not redact artifact bytes. Encryption or upload failure must leave preservation unconfirmed without a plaintext fallback. Runner termination can prevent final steps or artifact upload; use the workflow run's AWS role session and CloudTrail record to identify and reconcile its exact rule during incident handling. Offline helper tests cover ownership, ambiguous responses, and cleanup failures; they do not prove live AWS cleanup.

Each host-access invocation shares a 120-second deadline across its commands; AWS CLI requests have a 25-second subprocess cap, short connection/read timeouts, and one attempt. The backup helper shares a 540-second transfer deadline, bounds each SSH/AWS command, and uses SSH connection timeouts and keepalives. The transfer step has ten minutes. The unchanged full-deployment template has 41 minutes of step limits inside a 45-minute job, but its artifact path still requires correction. The inactive manual backup check has 28 minutes of step limits inside a 35-minute job, including three for cleanup, two for sealing and two for ciphertext upload. Its 30-minute OIDC session covers the conservative 23-minute authentication-through-upload budget. Ordinary command or transfer timeouts leave time for final steps. Runner termination or forced cancellation can still prevent them.

The SSH identity helper also bounds its nested AWS request to 25 seconds. The access controller gives that helper a separate process group; on deadline expiry or keyboard interruption it stops the group, including the nested request, and allows five seconds to reap the process and drain its captured output. An identity failure leaves the journal without an owned rule and stops before opening SSH. Credentials and captured service errors remain out of workflow output.

The separate source-only [journal preservation helper](ci-journal-preservation.md) now checks a pinned age dependency and public recipient, then seals exact journal bytes after cleanup through no-overwrite publication. It emits only ciphertext integrity metadata or fixed failure codes. Its local preflight uses public canary bytes and cannot prove off-host decryptability. The inactive manual backup template is wired to it through [private preparation and existing-object verification](existing-backup-check.md). Approved-recipient off-host verification and the actual runner/cleanup/upload path remain prerequisites before activation. The full-deployment template still needs separate integration and raw-artifact removal.

The inactive backup workflow now performs only a manual check of one independently pinned, already-transferred snapshot; it has no schedule or S3 write permission. The underlying `fetch-backup.py` still supports private operator transfers when `--existing-only` is absent. For a new object that mode hashes the downloaded ciphertext locally, then uses a conditional `PutObject` with an explicit SHA-256 and AES256 server encryption. Both the archive and checksum sidecar use `If-None-Match: *`: an existing conflicting key or a concurrent create stops the run without an unconditional overwrite. Existing archive reuse requires matching recorded SHA-256, exact byte length and AES256; the small checksum sidecar is read back and compared byte for byte, including legacy sidecars without metadata. Archive metadata alone is reported as `remote_metadata_matches`, never full ciphertext verification. `off_host_ciphertext_readback_verified` remains false: the operator must separately download and hash the complete S3 ciphertext before claiming that gate or restoring it.

The source helper now accepts `--expected-manifest PATH`, a private, current-owner regular JSON file containing exactly `name`, `bytes` and `sha256`. It refuses symlinks, group/other access, oversized files, invalid fields and stale snapshots before any SSH or AWS call. It reads that pin once and compares every field with the host's latest manifest before accessing S3; a newer latest snapshot fails the check instead of changing the selected snapshot. Keep this file out of logs and artifacts.

For a bounded check of an already-transferred snapshot, combine `--expected-manifest PATH --existing-only --public-output`. Missing or conflicting archive/sidecar objects fail without downloading an archive or creating either object; only the bounded checksum sidecar is downloaded for comparison. Success proves archive metadata and exact sidecar readback, not full off-host ciphertext readback, a new conditional upload, or SSH cleanup. `--public-output` emits only status and scoped verification booleans; the default output retains snapshot identifiers and byte counts for private operator evidence and must not be used in public workflow logs. These flags are now combined in the inactive manual backup template. This is source integration only: no active workflow, host helper, schedule, IAM role policy or recovery gate is changed by it.

New uploads are capped at **5,000,000,000 bytes** (decimal 5 GB), conservatively within the documented [single-PUT limit](https://docs.aws.amazon.com/AmazonS3/latest/userguide/upload-objects.html). This is distinct from the larger snapshot-manifest validation bound. Conditional multipart upload is unsupported; a larger new archive fails before download with `BACKUP_NEW_UPLOAD_EXCEEDS_SINGLE_PUT_LIMIT`. The runner CLI must support [`put-object --if-none-match`](https://docs.aws.amazon.com/cli/latest/reference/s3api/put-object.html); this was checked locally with AWS CLI 2.34.57. A conditional conflict or uncertain response is preserved as failure; there is no alternate-key or unconditional retry. Deadlines and the existing `daily/*` IAM scope remain unchanged. The existing-object check creates no snapshot, downloads no archive and modifies no application data; its session policy omits S3 writes.

After recovery, first reconcile the selected Terraform/IAM host and both protected identifier variables and preflight metadata secrets, with no outstanding SSH journal. Re-run the read-only OIDC identity check for that selected host. Follow the [manual existing-backup procedure](existing-backup-check.md) for the narrow check. A separate later transfer workflow must record OIDC authentication, AWS-verified SSH host keys, new archive transfer evidence, full off-host ciphertext readback, encrypted-journal recovery and successful terminal removal of the owned runner `/32`. Borrowed access proves no owned-rule removal. No transfer schedule is included in the current template; review one only after that separate manual transfer path has passed; GitHub environment branch rules do not by themselves require a human reviewer.

Keep full deployment separate. The active website overlay requires an explicitly reviewed [website reconciliation](website-releases.md); ordinary activation refuses it, and also refuses reactivating the same current base bundle. Do not remove either guard, relabel base manifests, or manufacture an upgrade merely to obtain a green workflow. A later real, reviewed application bundle must have its own compatibility/recovery plan and matching installed operator-tool hashes before the deployment path can be exercised. New helper source does not silently replace a helper embedded in an immutable historical bundle.

Runtime release builds target Linux x64 on Ubuntu 22.04 (glibc 2.35) and Apple Silicon on macOS 15 with a macOS 13 deployment target. GitHub's [runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) documents the hosted platforms. Release archives contain the executable, license, and README. Node SDK/MCP bundles, a Python wheel, installer and skill accompany the native archives; SHA256SUMS covers every asset. Existing tags and draft releases must match the source commit before assets can be replaced. A successful build is not a launch approval: the remaining gates in `docs/launch-requirements.md` still apply.
