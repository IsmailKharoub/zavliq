# Verification and release automation

The verification workflow builds and tests the website, control service, TypeScript/Python clients, MCP adapter, Synapse policy, and native runtime. It also runs the offline onboarding, load, installer, backup and private-stage monitoring contracts. It receives read-only repository access and no production credentials. Action dependencies are pinned to verified commit hashes; Node, pnpm, Rust, and Synapse versions are pinned.

Deployment and backup templates remain in `infra/github/` until the production environment is provisioned. Do not enable them before the AWS role, instance, repository environment, alerts, and restore drill have been verified.

The separate [production OIDC preflight](../../.github/workflows/production-oidc-preflight.yml) is manual, restricted to this repository's `main` branch and the `production` environment, and capped at five minutes. It checks out no source. The [pinned AWS action](https://github.com/aws-actions/configure-aws-credentials/blob/cbe3b392738ccf3f987d68400dafcf4b0624a56c/README.md) obtains a 15-minute OIDC session whose inline policy permits only `sts:GetCallerIdentity` and `lightsail:GetInstance` for the exact selected instance ARN in `us-east-1`. The identity operation uses `Resource: "*"`; the instance read does not. The job checks account, role session, instance name/ARN, region and running state, and emits only sanitized results. It opens no SSH access, changes no firewall, performs no S3 operation and activates nothing. A pass establishes authentication and instance identity, not application health, access cleanup, backup, deployment or restore verification.

Before a reviewed dispatch, add four **metadata-only environment secrets** to `production`: `AWS_ACCOUNT_ID`, `AWS_DEPLOY_ROLE_ARN`, `LIGHTSAIL_INSTANCE`, and `LIGHTSAIL_INSTANCE_ARN`. Take them together from independently verified **active** Terraform/AWS identity evidence; a prepared standby is not the selected host. These secret values are resource identifiers, never AWS access keys. Secrets provide log masking from the start of each step; ordinary environment variables would expose identifiers before an in-step mask ran. Missing or inconsistent identifiers fail before role assumption. The mutation templates still use their existing protected variables and remain inactive. When the selected host changes, update both those variables and the preflight metadata secrets consistently before rerunning. Review the environment's branch/reviewer policy separately; this workflow does not create protection rules or change IAM trust/permissions. The active website override still requires explicit reconciliation before any full deployment; this preflight does not bypass that boundary.

The deployment template accepts a pre-uploaded production bundle ID, its reviewed manifest SHA-256, and the expected current successful production manifest hash (`none` only for the first activation). It runs only by manual dispatch from this repository's `main` branch. There is no tag trigger or image/native build during deployment. The remote activation tools at `/opt/zavliq/production-tools/` must match the workflow checkout byte for byte before their activation command runs. Bundle IDs use `REVISION-public-CONFIGURATION_PREFIX`; application provenance remains the bundle's frozen revision even when later operator tooling has its own commit. See [production bundle preparation and activation](../../infra/production/README.md).

Before installing either workflow, configure the protected `production` environment with `AWS_DEPLOY_ROLE_ARN`, `AWS_ACCOUNT_ID`, `LIGHTSAIL_INSTANCE`, `LIGHTSAIL_INSTANCE_ARN`, and `BACKUP_BUCKET`, restrict deployment branches to `main`, and verify the exact immutable GitHub OIDC subject in the [hosting procedure](README.md#hosting-and-credentials). Take the instance name and exact ARN from the reviewed Terraform outputs together. The AWS action is pinned to the verified v6.2.4 commit and checks the expected account. Setting up the template does not create a GitHub environment or assume an AWS role; those live checks remain required.

The access helper accepts only the original production name or an explicitly selected `zavliq-production-recovery-<suffix>` name. Before obtaining access or changing a rule, `GetInstance` must match both that name and its exact ARN in the fixed account and `us-east-1`. The v2 journal stores the validated identity. Cleanup takes only the journal directory and continues against that saved identity even if protected environment values have changed; a reused name with a different ARN is refused. V1 journals have no ARN and must be completed with their original helper or explicitly reconciled before upgrading. Never change the active-instance IAM scope while an access journal remains outstanding. See [recovery-host adoption](recovery-host.md).

Both templates share one production host-access concurrency group. `ci-host-access.py` obtains the runner's public IPv4 address over verified HTTPS and preserves existing operator firewall rules. If access is already allowed, the run borrows it and does not remove it. Otherwise it journals ownership before requesting one TCP/22 `/32` rule. Returned Lightsail operation IDs are persisted before polling, and ownership is cleared only after a successful terminal close operation and confirmation that the exact rule is absent. A known pending open must settle before cleanup can succeed. If the open response was lost before an operation ID was recorded, cleanup attempts a close but retains ownership and reports `SSH_OPEN_OUTCOME_UNKNOWN_OPERATOR_RECONCILIATION_REQUIRED`: a delayed open is still possible, so the operator must reconcile the journal with AWS operation/CloudTrail evidence. The additional `lightsail:GetOperation` read uses `Resource: "*"` with a fixed `us-east-1` condition because this action has no resource-level scope in the [AWS IAM reference](https://docs.aws.amazon.com/service-authorization/latest/reference/list_lightsail.html). AWS-supplied host keys and an ephemeral SSH certificate are used. The final step attempts to close only the owned rule, then removes the temporary credential files even if closure fails. A cleanup failure preserves just the rule journal as a seven-day workflow artifact: instance, temporary runner CIDR, ownership state and sanitized operation IDs/statuses, with no credential files. A runner termination can prevent final steps or artifact upload; use the workflow run's AWS role session and CloudTrail record to identify and close its exact rule during incident handling. Offline helper tests cover ownership, ambiguous responses, and cleanup failures; they do not prove a live AWS cleanup.

Each host-access invocation shares a 120-second deadline across its commands; AWS CLI requests have a 25-second subprocess cap, short connection/read timeouts, and one attempt. The backup helper shares a 540-second transfer deadline, bounds each SSH/AWS command, and uses SSH connection timeouts and keepalives. The transfer step has ten minutes. Deployment step limits total 41 minutes inside a 45-minute job; backup step limits total 24 minutes inside a 30-minute job. These totals include three minutes for cleanup and two for failed-journal upload, so an ordinary command or transfer timeout leaves time for both final steps. Runner termination or forced cancellation can still prevent them.

The twice-daily backup workflow retrieves the latest encrypted archive created by the host timer, validates freshness and its checksum, uploads it to the exact private production bucket, and confirms the object metadata. It does not generate a snapshot or modify the database. All workflow templates remain inactive until the release owner installs and exercises them against production.

Runtime release builds target Linux x64 on Ubuntu 22.04 (glibc 2.35) and Apple Silicon on macOS 15 with a macOS 13 deployment target. GitHub's [runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) documents the hosted platforms. Release archives contain the executable, license, and README. Node SDK/MCP bundles, a Python wheel, installer and skill accompany the native archives; SHA256SUMS covers every asset. Existing tags and draft releases must match the source commit before assets can be replaced. A successful build is not a launch approval: the remaining gates in `docs/launch-requirements.md` still apply.
