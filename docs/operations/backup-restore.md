# Backup and recovery

The default recovery objectives are at most 24 hours of disaster-related loss and at most two hours to restore a fresh deployment. They are targets until a timed drill passes. Backup retention in S3 is seven days, with AWS lifecycle processing performed asynchronously. Live message/media retention and encrypted client key recovery are separate policies.

## Encryption and scheduling

Generate an age recovery identity **off the server** using `age-keygen -o /PRIVATE/OFFLINE/zavliq-backup.key`. Keep the private file in the operator's backed-up recovery store. Place only the generated public recipient into `/etc/zavliq/operations.env`. Never commit the private key, put it on Lightsail, or print it in a support transcript.

The systemd timer takes snapshots twice daily (02:15 and 14:15 UTC plus a small jitter). `backup.sh` serializes runs with a lock, pauses Synapse/control writers, exports PostgreSQL and copies application volumes and configuration, resumes writers even on failure, encrypts the archive with age, writes a SHA-256 checksum, and keeps seven days of encrypted local retries. Gateway requests can wait briefly during the consistent snapshot. Measure and record that pause under load; the first release must keep it below 30 seconds. If data growth makes that impractical, replace this strategy with a validated coordinated hot-snapshot implementation before increasing public quotas.

When enabled after its reviewed manual verification, the off-host workflow is scheduled at 02:43 and 14:43 UTC. It retrieves only encrypted archives over verified SSH and writes them to private S3 with AES256 server encryption and TLS. New archives are locally hashed against the snapshot checksum and uploaded with a conditional create plus explicit S3 SHA-256. Both archive and checksum-sidecar keys are preserved on conflict, including a concurrent create. Existing archive reuse checks recorded SHA-256, exact size and AES256; it does not read back the archive ciphertext. Sidecars are compared byte for byte. The helper reports these scopes separately and never equates matching metadata with full off-host ciphertext verification. Independently download and hash the complete selected S3 archive before restore or a full readback claim.

New uploads through this bounded helper must be no larger than 5,000,000,000 bytes (decimal 5 GB). Larger new snapshots fail before transfer and require a separately reviewed conditional multipart path; the manifest's larger storage bound does not authorize such an upload. See the [conditional-create limits and live verification sequence](ci.md). Lightsail has no S3 account credential; the ephemeral GitHub OIDC role may access only this deployment's backup prefix and temporary SSH APIs. Local success does not mean off-host success: the independent Lambda checks S3 timestamps and alarms if no backup is younger than 24 hours. GitHub schedule delay is expected; the duplicate daily run provides margin but is not an SLA.

The current private AWS staging deployment uses the separate 48-hour, fixed-object upload capability described in [private-staging-monitor.md](private-staging-monitor.md). Its first S3 upload and fresh standard-message restore passed on September 12, 2026; that evidence does not establish production workflow delivery or the final release's full recovery gate.

## Fresh-target recovery drill

1. Record the timer start, original server-name and source release. Provision an isolated host with the same architecture and PostgreSQL major version. Keep its DNS disconnected from the original network.
2. Download a selected `.tar.age` and checksum from S3 using operator access. Verify SHA-256 before decrypting; retain the exact source release images so schemas match. Never restore an unknown archive.
3. Follow the [production replacement procedure](../../infra/production/README.md#restore-an-existing-public-network-on-a-fresh-replacement-host). Use an empty replacement Docker daemon and retain the original `zavliq-production` project, `zavliq.com` server name and canonical HTTPS origin. Do not initialize new secrets or start containers. Upload the exact protected public bundle and prepare only the reviewed private operations configuration.
4. On the trusted off-host recovery machine, decrypt with the primary age identity, then encrypt the verified plaintext to a fresh single-use transport recipient. Keep the primary identity off AWS. The tool requires a reviewed receipt binding the original encrypted archive, transport archive, plaintext, exact image manifest and replacement host. `restore.py prepare` checks those bindings, consumes the matching transport key, restores original state into fresh volumes and starts private core services. The current snapshot format does not itself contain a public-manifest receipt, so the original backup-to-bundle binding requires operator review.
5. Fence all old writers and Echo before starting the replacement gateway and restored Echo. Restrict public traffic to verifiers while establishing certificate-verified canonical routing. The snapshot omits Caddy TLS/ACME state; certificate recovery, DNS/ACME and route choices need explicit review. Verify original devices, a standard DM/file, memberships, a pending request and block, quotas, an offline message, retained E2EE text/JSON/file and new bidirectional encrypted messages without changing client origin or keys. Confirm the restored Echo identity and an actual reply. Record exactly which cases were exercised. A server backup cannot decrypt client E2EE history by itself.
6. Supply the current verification/fencing receipt to `restore.py complete`. It checks local exact unpaused images and canonical HTTPS, takes a new encrypted backup, and adopts the restored state before enabling schedules. Verify off-host upload and monitoring separately before opening normal traffic. Measure elapsed recovery through routing and client verification, plus the age of recovered state, against the two-hour RTO/24-hour RPO. Rotate temporary SSH access and remove remaining one-use transport credentials; never allow two active networks with the same server name.

The production tool rejects unsafe/incomplete snapshots and existing replacement state, preserves failed attempts and volumes, and never provisions a new Echo device or rewrites the namespace. Its offline tests do not establish a live production recovery time. The generic `infra/scripts/restore.sh` belongs to the older diagnostic path and must not be used with the public bundle's image overlay. An incompatible-schema rollback uses the reviewed pre-deploy snapshot and exact matching public bundle through the replacement procedure.

For the final private AWS candidate, [the E2EE restore fixture](e2ee-restore-fixture.md) preserves two original device stores and verifies previously unseen encrypted text, exact JSON and an attachment after a fresh-volume restore. Its two phases use the same local tunnel origin; operations owns the temporary source-to-clone route change.
