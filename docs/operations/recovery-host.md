# Adopting a distinctly named production recovery host

This is an operator procedure, not automatic failover. Zavliq is a public beta: an older snapshot cannot be adopted while silently discarding writes accepted afterward. The drill requires an explicit maintenance window and a final consistent snapshot after the public-write fence. Terraform defaults create no replacement and keep `aws_lightsail_instance.app` active. No recovery host name or verification address is preselected. Both instance resources retain destruction protection.

1. Schedule and communicate the maintenance window. Stop deployment and off-host backup CI runs and complete every temporary SSH access journal. Preserve current Terraform state, bundle manifests and prior recovery evidence. Review the cost of all simultaneously retained hosts, backups and transfer before adding another `medium_3_0` instance; this option creates another billable host and does not enlarge the account budget.
2. Choose an explicit, distinct `zavliq-production-recovery-<suffix>` name. Set only `replacement_instance_name` in private reviewed inputs, leaving `active_instance = "original"`, `replacement_ingress_phase = "verification"` and both confirmation flags false. The expected change adds a recovery instance and operator-only TCP/22 firewall. Original instance, static-IP attachment, exact GitHub IAM scope, bucket, monitor, OIDC role and DNS stay selected. Review a saved plan before applying it.
3. Verify the new host's pinned Docker/Compose versions and containerd image store. Transfer the reviewed bundle and confirm all five exact image IDs. Keep application ingress and Echo stopped. Package preparation can precede maintenance; restoration from the final snapshot cannot.
4. Enter the maintenance fence on the source **before the final snapshot**. Close all operator-controlled fixture and browser device stores. Stop the source gateway and Echo, stop backup/retention/health timers and other automation capable of changing or restarting the application, and let already-running maintenance jobs finish or settle safely. Recheck that gateway and Echo remain stopped, public requests cannot reach Matrix/control, no deployment or maintenance writer is active, and all in-flight public requests have settled. Preserve the fence across the snapshot operation. Public clients may retain unsent local outbox entries; the server must accept no new public writes during this window.
5. Take the final consistent encrypted snapshot while source Synapse/control/Postgres remain available for the backup tool. Record the fence and snapshot timestamps, exact application/backup binding, archive checksum and verified off-host ciphertext readback. The current backup tool briefly pauses writers and then **unpauses Synapse/control**; it does not maintain the public-write fence itself. Gateway, Echo, timers and other access paths must stay fenced throughout. After backup completion, stop the source core and verify that all source writers remain stopped. If any public write or uncontrolled device progress occurred after the selected snapshot, that snapshot is no longer the cutover candidate: preserve the evidence and repeat the fenced final-snapshot process before proceeding.
6. Restore only that final snapshot into the replacement's fresh volumes using the reviewed production recovery entrypoint. Keep replacement gateway/Echo stopped and run the private core/image/data checks first. Preserve the original host and volumes unchanged. Original and restored Echo/device state must never run concurrently. Record successful private checks, source shutdown and the absence of outstanding CI journals before setting `replacement_cutover_confirmed = true`.
7. Transfer the canonical route in a separately reviewed **restricted-verification** change: set `active_instance = "replacement"` while leaving `replacement_ingress_phase = "verification"`. Supply explicit verifier IPv4 `/32`s in `replacement_verifier_cidrs` and the reviewed post-attachment self-Echo egress `/32` in `replacement_echo_cidr`. The module closes original public application ingress and waits for both firewalls before reattaching the **existing** static IP. The replacement permits public TCP/80 for Caddy ACME HTTP-01/redirects, TCP/443 only from the exact verifier/Echo address union, and no UDP/443. SSH remains operator-only. Check the actual Echo egress route; an IP guessed from the pre-attachment host is insufficient. The A record retains the same static IP, and GitHub instance IAM changes to the replacement's exact ARN. This step keeps ordinary users in maintenance.
8. With restricted canonical routing established, start the replacement gateway for the canonical certificate and trusted HTTPS checks. Verify HTTP only serves ACME/redirects and does not expose Matrix/control over plaintext. Start only the restored Echo worker once the source is proved stopped. Reopen the original controlled client stores against the unchanged canonical origin, verify retained E2EE text/JSON/file and new exchanges, verify restored Echo and complete the production restore record with measured timing. A failed check leaves public opening blocked; retain state and investigate without silently reverting to a stale database.
9. After those checks and the restore-complete step pass, review a separate plan setting `replacement_ingress_phase = "public"` and `replacement_verification_confirmed = true`. Only this later gate opens replacement TCP/443 and UDP/443 to the public. Verify canonical service behavior and resume approved replacement maintenance timers and user access. The source remains stopped and SSH-only. Coordinate expected maintenance alarms; restricted verification is not evidence of continuous public availability.
10. With CI still stopped, update protected GitHub `LIGHTSAIL_INSTANCE` and `LIGHTSAIL_INSTANCE_ARN` together from the selected outputs. Keep the existing account, production role, bucket, region and immutable repository/environment trust. Validate actual `GetInstance` name/ARN, then exercise bounded access and journal cleanup before enabling either inactive workflow template.

The two confirmation inputs attest to separate operator checkpoints. Cutover confirmation covers the final fenced snapshot, stopped source and private restored-core checks. Verification confirmation covers later canonical TLS, original-device recovery, restored Echo and restore completion. Terraform checks the explicit inputs; it cannot prove database consistency, maintenance fencing, client behavior or that an earlier phase actually ran.

The access helper records name, ARN and account in its v2 journal. Cleanup follows that journal, never newly selected environment values, and refuses an AWS name that now resolves to another ARN. Existing v1 journals lack an ARN: finish them with their original helper or reconcile them explicitly before switching tools or IAM scope. CI IAM always grants one exact instance ARN, without a wildcard or dual-host grant.

Do not remove or rename the original Terraform resource, reuse its AWS name, move its state to the new resource, or automatically switch back after replacement writes. Even controlled verification messages and crypto-device progress can make the databases diverge. Returning to the retained original needs an explicit data-consistency and routing plan; changing the selector alone is insufficient.

Source checks include Terraform formatting/validation and eleven isolated [mock-provider](https://developer.hashicorp.com/terraform/language/tests/mocking) scenarios for defaults, standby, restricted cutover, CIDR requirements and separately confirmed public opening. Run `terraform -chdir=infra/terraform test -filter=tests/recovery.tftest.hcl` with Terraform 1.15.x; both providers are mocked and no AWS credentials or live state are used. These checks do not replace the fresh-host and restore verification above.
