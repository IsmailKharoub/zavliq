# Zavliq Synapse policy

Load `zavliq_policy.ZavliqPolicy` as a Synapse module with a persistent absolute `database_path`, normally `/data/policy.sqlite`. The launch deployment pins Synapse 1.160.0 and uses a single writer. Configuration is generated by infrastructure scripts; public federation and native registration remain disabled.

Room state `com.zavliq.conversation` contains `{kind: "dm" | "group" | "channel", encryption: "standard" | "e2ee"}`. It is also copied into immutable room creation content so policy checks remain correct while Synapse emits initial state in stages. The mode cannot later change or be redacted. Private encryption uses `m.room.encryption` with `m.megolm.v1.aes-sha2`; channels are standard mode. Private room histories begin at invitation time, preserving a first message sent before acceptance.

The module enforces:

- Exact local invitations, one pending request per unfamiliar directed pair, five new contacts per day, rejection cooldown, and owner-specific blocking. An accepted relationship persists independently of later group invitations.
- Invite-only DMs/groups, no guest access, two DM members, 100 group members, and 1,000 channel subscribers. SQLite reservations prevent concurrent membership additions from exceeding capacity.
- Public directory publication only for channels. Channel defaults require publisher power for messages; raw power-level updates cannot permit subscriber posting.
- Immutable conversation privacy and encryption, no plaintext messages/receipts in encrypted rooms, and no encrypted payloads in standard rooms.
- 32 KiB serialized event content, 30 messages/minute, and 1,000/day. Standard delivered receipts use a separate 90/minute and 3,000/day budget. Encrypted receipts are indistinguishable from messages and count toward the message budget. Configuration/state changes have a separate bounded budget, so custom event types cannot become an unmetered delivery path.
- Hidden-by-default user directory results. Exact profile lookup is available to authenticated local identities.

Limits, blocks, accepted relationships, and event-accounting IDs survive restarts. Event bodies, access tokens, and encryption keys are not stored in the policy database. Failed or uncertain operations can conservatively consume admission or quota capacity. Normal message delivery and deduplication remain the responsibility of Matrix/Synapse.

Authenticated resources under `/_synapse/client/zavliq/` provide `blocks`, `profile`, `directory`, and `quotas`; `health` is public. `POST login-token` creates a short-lived Matrix login token for the authenticated owner only, for controlled new-device pairing (ten/day). These use `ModuleApi` authentication and JSON request handling. Personal blocks prevent DMs and new invitations but cannot silence publishers or veto membership in existing shared groups/channels.

Run the pinned native-import tests from the repository root:

```sh
PYTHONPATH=services/synapse-policy uv run --no-project --with matrix-synapse==1.160.0 python -m unittest discover -s services/synapse-policy/tests -v
```

Tests include real Synapse Rust-backed event content, room-state order, encryption boundaries, invitation isolation, concurrent quota reservations, profile ownership, persistent counters, and blocking without room-wide moderation authority. Follow with the control service's live integration script after rebuilding Synapse; mocks cannot establish compatibility with the actual room-creation lifecycle.

Callback references: [module API](https://element-hq.github.io/synapse/latest/modules/writing_a_module.html), [spam callbacks](https://element-hq.github.io/synapse/latest/modules/spam_checker_callbacks.html), [third-party room callbacks](https://element-hq.github.io/synapse/latest/modules/third_party_rules_callbacks.html). Third-party event callbacks are experimental upstream, so every Synapse version change requires these tests and live integration before rollout.
